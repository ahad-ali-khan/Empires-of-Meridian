Role and operating rules

You are the principal engineer, technical game designer, UI engineer, tools engineer, and test owner for an original browser-based real-time strategy game. The working title is Empires of Meridian. It is inspired by the tempo and strategic depth of classic age-progression RTS games, especially the qualities players value in Age of Empires III, but it must not reproduce protected expression from any existing game.

Build the game in the repository you have been given. Do not merely write a design document, mock the screens, or scaffold empty services. Deliver working, tested increments in the order defined below.

Follow these rules throughout the project:

1. Never copy or download Age of Empires assets, music, sound effects, UI textures, icons, fonts, models, map layouts, code, dialogue, names, faction rosters, campaign plots, or exact balance data.

2. Do not call the game, modes, progression system, factions, resources, buildings, or units by Age of Empires names when a distinctive name would create confusion. Generic genre terms such as villager, cavalry, barracks, formation, skirmish, minimap, and fog of war may be used where appropriate.

3. All shipped content must be original, generated by this repository's own procedural tools, created specifically for the project, or obtained under a documented license that permits redistribution. Maintain THIRD_PARTY_ASSETS.md with source, author, URL, license, modifications, and attribution requirements for every non-original asset.

4. Do not claim production quality while using silent buttons, fake matchmaking, scripted combat, random result screens, non-authoritative clients, or placeholder boxes. Label incomplete work in PROJECT_STATE.md.

5. Do not attempt the whole game in one unverified pass. Complete the milestones and their acceptance tests in order. A later milestone may not conceal a failing earlier gate.

6. Keep the project runnable after every meaningful commit. Use conventional commits. Never commit secrets, generated build output, dependency caches, database volumes, or licensed source files that cannot be redistributed.

7. If a library or platform has changed since this prompt was written, verify its current official documentation, choose a maintained stable release, pin the exact version, record the choice in docs/adr, and update tests. Do not install floating latest versions in CI.

8. When the session or context is ending, update PROJECT_STATE.md with the last verified commit, commands that pass, known failures, current milestone, next three concrete tasks, and any decision that another agent would otherwise have to rediscover.

9. Prefer simple, inspectable systems over speculative engine abstractions. Add an abstraction only when at least two real consumers need it.

10. Keep simulation code independent from rendering, React, browser globals, network transports, and persistence. The same simulation package must run in Node and in a browser worker.

Product definition

Create a premium desktop-browser RTS with the readability of a tabletop battlefield and the tension of a 25-to-45-minute competitive match. Players explore a procedurally generated frontier, establish a settlement, gather four resources, choose how to advance through five eras, field counter-based combined armies, contest trade routes and neutral alliances, earn off-map dispatches, and destroy or outscore opponents.

The experience must support:

Offline tutorial, skirmish, campaign, challenge scenarios, and replays.

Online private lobbies, public custom lobbies, unranked quick match, ranked matchmaking, team games, free-for-all, spectators, reconnection, post-game statistics, text chat, and team voice chat.

Mouse and keyboard as the first-class control method, with fully remappable hotkeys and a coherent grid layout.

One to eight human or AI players depending on the map and mode.

At least eight asymmetric factions at content-complete release.

Five eras, four economic resources, one off-map renown resource, over forty reusable unit archetypes, faction-unique units and technologies, naval play, walls, gates, artillery, siege, formations, stealth, garrisoning, trade, neutral alliances, treasures, and destructible buildings.

A data-driven scenario and random-map system.

A polished front end, lobby flow, match HUD, loading experience, original adaptive score, layered soundscape, readable VFX, satisfying animation, and strong performance on ordinary hardware.

This is a desktop-first game. Do not weaken selection, hotkeys, or information density to force full phone support. Tablets may receive a read-only replay viewer later. The minimum interactive viewport is 1280 by 720. Support 16:9, 16:10, ultrawide, and windowed layouts without stretching the world view or clipping the HUD.

Experience pillars

Every feature must support at least one of these pillars:

1. Readable consequence. A player can see why an exchange, resource shortage, technology, or positioning choice mattered. Silhouettes, health changes, projectile timing, selection responses, combat barks, and UI values must agree.

2. Pressure with recovery. Scouting, raids, trade routes, dispatch timing, map control, and era advancement create urgency, while town defenses, counter-units, retreat paths, and comeback objectives prevent one early mistake from becoming a long, hopeless cleanup.

3. Asymmetric mastery. Factions share a learnable core but bend economy, military composition, era choices, dispatches, or map control in unmistakable ways.

4. Low-friction command. Selection, control groups, contextual orders, formations, production queues, camera movement, alerts, and hotkeys respond immediately and consistently.

5. Battlefield spectacle without visual fog. Smoke, debris, volleys, formations, ships, and collapsing structures feel weighty, but effects never obscure unit identity, cursor targets, health, range, or terrain.

Original world and visual identity

Set the game in Meridian, a fictional early-industrial world shaped by ocean trade, city leagues, inland confederacies, and contested frontier provinces. Technology moves from late sail and black-powder warfare toward early rail, foundries, field telegraphy, and precision artillery. Avoid a direct mapping between a faction and one real ethnicity. Use cultural consultation if later content draws closely from living cultures.

The art direction is painterly strategic realism:

Three-quarter elevated camera with physically plausible scale compressed for playability.

Warm natural daylight, cool readable shadows, rich earth, forest, stone, faded cloth, oxidized metal, and faction colors used as identification accents rather than coating every surface.

Slightly exaggerated unit silhouettes, weapons, hats, packs, and banners so roles remain readable at normal zoom.

Buildings feel inhabited: workers, smoke, doors, pulleys, flags, storage piles, scaffolds, damage states, and era upgrades alter the silhouette.

Terrain uses blended macro color, detail normals, decals, cliffs, water foam, roads, snow or mud response, and local ambient props. Avoid noisy photogrammetry.

UI resembles a refined field atlas and command desk, using dark charcoal, warm parchment, muted brass, ink, and restrained faction accents. Do not imitate AoE III's panels, icons, frames, typefaces, proportions, or menu compositions.

Menus should feel calm and expensive, not overloaded with animated particles, glass cards, excessive gradients, or icon-only controls.

Create an original wordmark and simple geometric crest for the working title using SVG paths created in the repository. Do not imitate the Age of Empires logo treatment.

Dispatch deck and Renown system

Create an original off-map support system called Dispatches. Before a match, each player selects a 24-card field charter from a faction collection. Dispatches include resource convoys, workers, military detachments, technologies, fortification kits, naval support, mercenary contracts, and rule-changing upgrades.

Rules:

Renown fills a segmented meter. Each completed segment grants one dispatch token.

Dispatch costs are one or more tokens. Strong late cards require later eras and longer arrival times.

Most one-time dispatches may be sent once. A small explicitly tagged class becomes repeatable in the final era with increasing cost.

A queued dispatch can be canceled before departure for a full token refund. After departure it cannot be canceled.

Deliveries require an eligible arrival building or rally site. If every arrival site is destroyed, the dispatch waits and warns the player.

Arrival is telegraphed by a banner, sound, countdown, and minimap pulse. Opponents hear or see it only within line of sight.

Deck choice is locked once the match begins. Ranked opponents may inspect the faction but not the exact deck until the post-game screen.

Include starter decks named Expansion, Pressure, Defense, Alliance, and Naval. Names are generic labels, not copied card sets.

The deck builder supports filters, search, era columns, drag ordering, duplicate rules, validation, tooltips, unsaved-change protection, import/export codes, and versioning when balance patches change cards.

Dispatch definitions are pure data with effect scripts limited to a safe, deterministic command API. Never execute arbitrary user JavaScript.

Combat simulation

Implement combat as a deterministic fixed-tick system.

Each attack follows acquire, face, wind-up, release, recovery, and reacquire states.

Damage occurs at a defined release event or projectile impact, never at an arbitrary animation percentage that differs by frame rate.

Projectiles have deterministic trajectories. Visual interpolation may be smooth, but collision and impact are simulation events.

Units do not fire through terrain or solid structures unless the weapon is explicitly indirect fire.

Accuracy may use deterministic seeded spread. The same command log and seed must produce the same impacts on every supported client and the server.

Melee units reserve reachable engagement slots around targets to reduce clumping. If all slots are occupied, they seek another nearby legal target or support the formation rather than vibrating.

Friendly units use soft avoidance and formation slots. Enemies and buildings create hard blockers according to size and movement class.

A unit attacked in melee suffers a modest cohesion penalty to acceleration and disengagement, with immunity windows and caps. This creates commitment without an opaque permanent snare.

Focus fire is legal. Overkill reduction is an AI and formation behavior, not a rule that ignores player orders.

Units have stances: aggressive, defensive, stand ground, and no attack. Stance affects autonomous acquisition only, never explicit orders.

Commands include move, attack target, attack move, patrol, guard, stop, hold, deploy, undeploy, repair, heal, gather, build, garrison, ungarrison, board, unload, rally, set formation, use ability, and delete with confirmation.

Elevation and cover may modify line of sight and incoming projectile accuracy through simple exposed rules. Do not create a hidden simulation that players cannot read.

Healing does not occur while a unit is actively taking damage unless an explicit ability says so. Engineers repair machines and buildings; medics heal biological units.

Commander units grant capped auras and active abilities. They are valuable but never mandatory heroes capable of deleting an army alone.

Formations and movement

Support line, column, spread, square, wedge, and loose formations where valid. Naval formations use line ahead, line abreast, screen, and convoy ring.

A formation command computes stable slots relative to the group's centroid and facing.

Assign slots by movement class and role, keeping fragile ranged units behind screens and artillery in rear positions unless the player uses a custom arrangement.

The group follows a shared corridor generated by hierarchical pathfinding, while units use local steering to reach slots.

Formation width contracts at chokepoints and expands afterward without reordering the entire group every tick.

Mixed-speed groups use a group pace by default. Holding a modifier while issuing move allows faster units to move independently.

Attack move advances toward the destination, acquiring legal targets within stance radius, then resumes when targets are gone.

Patrol repeats a route and uses stance rules. Guard stays near a target and intercepts threats without chasing indefinitely.

Provide visible destination pips, formation previews, invalid-path feedback, and a subtle route line for selected groups when enabled.

Never allow units to spin, oscillate, stack into one point, or take a wildly longer path because one formation slot is blocked.

Use a two-level navigation system: coarse sectors or portals for long routes and a fine navigation grid for local paths. Cache integration or flow fields for large groups sharing a destination. Recompute only affected regions when buildings, gates, walls, bridges, ice, trees, or scripted blockers change. Run expensive path work in workers with a deterministic job order.

Environmental systems terrain weather water wildlife and biomes

The battlefield must feel alive, but it must not become a pile of expensive, unreadable, random simulations. Implement an explicit environmental-system contract. The same seed, map recipe, game settings, and authoritative command log must resolve the same gameplay-relevant environment on the server and every client. Rich visual motion may vary smoothly per device only where it cannot change a command result, path, line of sight, resource amount, hitbox, or outcome.

Research lesson: seasonal strategy games work because a player can read, predict, and prepare for an environmental pressure rather than being ambushed by invisible randomness. Treat weather and terrain as legible systems with forecast, cause, effect, counterplay, and clear boundaries. Do not turn every match into a survival game. Standard competitive play remains an RTS first.

Every chunk stores height, slope, surface class, soil or rock family, buildability, passability, water depth, shoreline distance, vegetation density, habitat tags, ambient zone, and optional fuel, wetness, snow, or scorch value. Derive visual meshes, navigation costs, decals, sound, particles, and prop placement from these shared fields.

Surface classes at minimum: packed earth, grassland, forest floor, mud, farmland, sand, dune sand, rocky ground, scree, cliff, shallow water, deep water, marsh, snow, ice only in explicitly supported scenarios, road, bridge, rubble, and burned ground. Each class defines movement cost and allowed movement classes; building and wall placement rules; footprint, wheel-track, hoof-print, dust, mud, snow, splash, and sound response; visual material layers and LOD policy; and whether it can carry resources, support a tree, burn in scenario modes, retain wetness, or host a water edge.

Use height and slope to form strategic terrain. Cliffs are not merely a texture: they create impassable boundaries except at authored ramps, passes, lifts, bridges, or scenario routes; they block or reduce line of sight according to the same approximation used everywhere; and they affect artillery position, chokepoints, camera limits, and build placement. Do not create pixel-thin cliffs, inaccessible resource spawns, one-way traps, or hidden firing shelves. The map validator must test every start, resource, treasure, trade site, dock site, crossing, and neutral objective for reachable legal routes.

Biome recipes must drive correlated detail rather than randomly scattering unrelated assets. A river basin has deposited lowlands, reed edges, wet banks, broadleaf clusters, shallow fords, muddy cart tracks, waterfowl ambience, and floodplain farms. A highland valley has exposed bedrock, steep scree, conifer bands, cold streams, windier ridges, and narrow passes. A dune sea has slip-faced dunes, wind-packed ridges, rocky outcrops, sparse thorn scrub, dry washes, caravan paths, heat haze, and oasis vegetation only where a water-table tag permits it. A volcanic frontier has dark rock, ash, hardy scrub, steam vents, scorched soil, and no arbitrary green lawn.

Use map-scale climate constraints: light palette, elevation, coastal exposure, moisture, temperature band, and prevailing wind. These are recipe inputs that explain why assets occur together. They are not a request to simulate continental climate in real time.

Vegetation grass greenery crops and fire

Vegetation has four practical tiers:

1. Strategic forest and crop entities. Harvestable trees, plantations, orchards, farms, and scenario fuel patches are authoritative. Their removal, regrowth where enabled, and line-of-sight or pathing consequences are deterministic.

2. Gameplay cover clusters. Defined forest edges, reed beds, hedges, and brush zones may affect sight or movement only when their boundaries are represented in authoritative terrain data. Never infer cover from a decorative mesh.

3. Reactive ground cover. Grass, flowers, shrubs, crop rows, reeds, fallen leaves, and loose sand are presentation instances. They bend under wind and nearby actors, flatten under feet, wheels, construction, or battle pressure, then recover through a cheap local field. This is cosmetic unless an explicit authoritative crop or cover zone says otherwise.

4. Distant ecological dressing. Far-tree cards, background forests, horizon silhouettes, and distant haze are noninteractive and aggressively culled.

Use plant communities per biome: meadow grass and deciduous saplings on temperate flats; conifers, moss, and low scrub at altitude; reeds and water plants near marsh or river tags; hardy shrubs and palms only around oasis tags; sparse dry grass, thorn scrub, and wind-scoured rock in desert. Avoid uniform carpet grass, clone forests, or a desert that is simply yellow terrain with the same trees.

Wind is hierarchical. A global weather vector affects clouds, flags, smoke, tall trees, medium bushes, grass, crop tops, sails, hanging cloth, dust, and water in different amplitudes and phase offsets. Use GPU vertex deformation, instancing, and distance bands for presentation. Do not update individual grass entities on the CPU. Nearby movement writes a small local bend field sampled by shaders; large explosions create a temporary radial disturbance; rain makes leaves and grass darker and reduces dust. None of this changes pathing or combat.

Forests are resources and battlefield geometry. Harvesting removes authoritative tree entities, leaves stumps and disturbed ground, opens sight lines and movement space, changes local ambience, and replaces dense canopy with matching regrowth or cleared-ground presentation. Regrowth is off in standard competitive matches unless a specific mode declares a slow, visible, deterministic regrowth rule. Farms use stage-based crop meshes: tilled, planted, growing, harvest-ready, and exhausted or fallow. They are readable at strategic zoom and do not demand a fake agricultural simulation.

Fire is tiered as well. Normal building fire, cannon smoke, torches, and burning debris are presentational effects tied to authoritative damage events. Optional environmental fire for campaign, cooperative, or scenario play uses deterministic ignition cells, fuel, wetness, wind class, spread order, firebreaks, and clear UI warnings. Dry vegetation can burn; wet ground and stone do not; rain suppresses visual intensity and, where that optional hazard is enabled, reduces spread. Never enable random spreading wildfire in ranked standard play.

Water shorelines rivers oceans and weather response

Water is a set of gameplay-defined bodies with separate bathymetry, navigable polygons, shoreline masks, flow or current class, wave-exposure class, dock and beach rules, and visual material parameters. Boats navigate authoritative water polygons and avoid one another through the same deterministic movement rules as land units. Do not use the animated water surface for collision, selection, projectile results, or ship position.

Rivers have source-to-mouth direction, shallow edge masks, fords, bridge anchors, bank slope, reed zones, and current visuals. Most RTS rivers use a static water level during standard matches. Flooded crossings or changing water levels belong to declared scenario events with precomputed alternate navmeshes and clearly visible countdowns.

Coasts use depth-based color, shore foam, wet-sand bands, beach decals, rock shelves, dock markers, waves scaled by wind exposure, and wake interaction. Reflections, refraction, caustics, and screen-space effects scale by quality tier and never determine gameplay readability.

Rain adds ripples, drops, runoff streaks, puddles in authored depressions, damp material response, reduced dust, softer distant contrast, and rain audio. It does not create arbitrary new water obstacles in ranked play.

Wind changes wave direction, foam breakup, sail and flag motion, smoke drift, dust direction, and bird flight pattern. Default competitive wind does not alter projectile ballistics, ship speed, unit accuracy, or gathering rate. A scenario may opt into those effects only with exposed numbers and counterplay.

Shallow water triggers splashes, darker wet lower legs, hoof or wheel resistance visuals, and appropriate footstep audio. It is passable only where its surface class and depth flags permit it. Units do not walk across every attractive shoreline.

Ships produce bow waves, stern wakes, wake decay, shore reflections, cannon water impacts, rain ripples, damage smoke, sinking bubbles, and debris. Pool all effects and remove them with entity lifecycle events.

Fish are a real economic resource only at authored fishing grounds. A fishing ground has deterministic stock, regeneration policy, occupancy limit, depletion visibility, shore or boat access rules, and safe path validation. Visible fish schools, jumping fish, and waterfowl are local presentation agents sampled from that ground's state. They never become thousands of authoritative entities.

Animals birds fish and ambient life

Create an AmbientLifeSystem and a separate ResourceAnimalSystem. The separation is non-negotiable.

Resource animals are authoritative gameplay entities. Hunt animals spawn in fair, validated herds with species size, food value, alert radius, fear threshold, flee route, regroup behavior, despawn rules, and movement constraints. They react to shots, nearby units, fire, and sudden construction in deterministic tick order. Herdable livestock use follow, graze, flee, herd, deposit, fatten, slaughter, and dead states; they must not be able to path through walls, cliffs, enemy territory rules, water, or buildings. Their movement must be predictable enough for skilled herding and never produce a seed-luck economic loss.

Ambient life is visual and audible dressing. Birds perch, forage, take off from nearby battle, follow broad wind direction, circle above water or cliffs, and form distant flocks. Small mammals use short habitat paths, pause, flee visual threats, and return after a cooldown. Fish school near shallow, sheltered water and disperse near wakes or explosions. Insects appear only at close range in suitable warm, wet, or floral zones. These creatures have no hitboxes, no targetability, no line-of-sight consequences, and no network replication.

Animal behavior should be ecologically plausible without pretending to recreate an ecosystem. Use habitat, food, water, cover, time-of-day, weather, and disturbance as weighted inputs. Dawn and dusk increase bird and animal ambience; rain reduces some bird activity and adds amphibian or wetland ambience; heavy battle disperses nearby ambient life; quiet returns gradually. Do not spawn a deer on exposed dune crests or a flock of seabirds in a boreal interior without a habitat tag.

Wildlife must never become a caricature of a real culture or region. Use familiar ecological behavior but original species names, silhouettes, sounds, and lore for Meridian where needed.

Multiplayer architecture

Use a server-authoritative deterministic command simulation.

The shared simulation runs at 20 fixed ticks per second in packages/sim in a Web Worker on clients and in the authoritative Node game room on the server.

Clients send compact intent commands for a future simulation tick. The server authenticates ownership, validates legality, rate-limits commands, orders them deterministically, and broadcasts the accepted command batch.

The server never trusts client positions, damage, resources, production, visibility, cooldowns, scores, or victory claims.

Clients may optimistically render selection feedback and command markers immediately, but gameplay changes apply through the agreed command stream.

Use integer fixed-point state and a shared seeded PRNG. Generate a canonical state checksum at regular intervals. A mismatch triggers telemetry, one recovery attempt from a compressed authoritative snapshot, and match quarantine if it persists.

Store periodic compressed snapshots and the complete accepted command log. Replays are initial seed plus content hashes plus commands plus optional snapshots for seeking.

Spectators receive delayed command streams in ranked games. They may seek only within buffered history and cannot communicate with active players through match channels.

Reconnection authenticates the player, sends the latest snapshot and subsequent command log, restores control groups where possible from client metadata, and resumes after checksum agreement.

Initial input delay adapts by region and measured RTT within a bounded 3-to-8-tick range. It may change only through a synchronized server event.

If a player disconnects, the match continues for a 120-second reclaim window. Custom lobby options choose no takeover, defensive AI takeover, or full AI takeover. Ranked uses defensive takeover, then converts to full takeover after the reclaim window.

A player may resign at any time. Team surrender requires a visible vote with cooldown and majority rules. Eliminated players become team spectators and lose enemy information beyond team vision until the match ends.

Pausing is disabled in ranked multiplayer. Custom games may allow a limited tactical pause pool approved by lobby settings.

Use Colyseus or a demonstrably better maintained equivalent for WebSocket rooms, matchmaking integration, reconnection, and transport. Keep the game protocol behind an adapter so the simulation does not import framework classes. Use Redis-backed presence and room discovery when scaling beyond one process. A room belongs to one authoritative process for its lifetime; never split one match simulation across general web functions.

Threejs rendering architecture

Use Three.js for all in-game 3D rendering. Start with WebGPURenderer; use its WebGL 2 backend or a verified WebGLRenderer path when required by compatibility. Detect capability, run a small benchmark, and choose Low, Medium, High, or Ultra defaults. The settings screen must show the active backend.

Architecture boundaries:

packages/sim owns authoritative entities and numbers.

packages/presentation maps immutable simulation snapshots and events to visual intents.

apps/web/src/game/renderer owns Three.js scenes, cameras, materials, LOD, animation, VFX, picking proxies, and resource disposal.

Never make every simulation entity a heavyweight React component or synchronize the Three.js scene through React state each frame.

Use an entity-view registry with pooling. Creation, update, and removal occur from snapshot deltas.

UI runs in React DOM over the canvas. World-space labels use a batched overlay or sprite system, not one DOM node per unit.

Rendering requirements:

Load authored assets as glTF 2.0 when used. Support Meshopt or Draco geometry compression and KTX2 or Basis textures. Verify decoder licensing and self-host decoders.

Use InstancedMesh, batched meshes, texture atlases, merged static geometry, and pooled materials for trees, rocks, projectiles, decals, rubble, repeated props, and simple units where animation strategy permits.

Skinned units use shared skeleton and animation data per archetype. Investigate instanced skinned rendering for mass armies; keep a reliable individual-skinned fallback for near-camera or unique units.

LOD0 for close inspection, LOD1 for standard play, LOD2 for far zoom, and impostor or simplified markers only at extreme distance. LOD changes must not pop conspicuously or change selection bounds.

Use frustum culling, distance culling, occlusion approximations where profitable, shadow cascades with stable texel snapping, and quality-scaled shadow casters.

Terrain uses chunked geometry, splat or array textures, normals, decals, and water intersections. Rebuild only changed chunks.

Water has readable shorelines, reflections scaled by quality, wakes, foam, and underwater tint. It must not dominate GPU cost.

Warm sun, hemispheric fill, limited local emissive effects, fog or atmosphere, and restrained color grading. Avoid expensive screen-space effects that make units blurry.

Compile shaders during loading to prevent first-volley or first-building stutter. Cache pipelines where the browser supports it.

Handle graphics context loss and restoration. Dispose geometries, materials, textures, render targets, mixers, audio nodes, and workers when leaving a match.

Provide a debug HUD for fps, frame time, simulation time, worker queues, draw calls, triangles, textures, GPU memory estimate, entities, path jobs, network rate, RTT, input delay, checksum, and snapshot size.

Models and procedural asset pipeline

The repository must contain a complete legal asset path. Three.js is the runtime renderer, not a substitute for an art department. For the first playable milestones, create original stylized models through deterministic TypeScript mesh factories using BufferGeometry, primitives, lathed profiles, extrusions, curves, merged geometry, generated UVs, and palette materials. The result should look intentional, not like default cubes and capsules.

Procedural model requirements:

packages/asset-tools contains factories for modular bodies, heads, hands, coats, packs, hats, shields, melee weapons, rifles, tools, cannons, wheels, ships, foliage, rocks, walls, roofs, windows, scaffolds, smoke stacks, flags, and terrain props.

Each faction has a shape language, palette, material roughness range, architectural kit, trim vocabulary, banners, and equipment motifs. Avoid real-world sacred motifs or direct cultural copies without review.

Unit proportions favor silhouette: slightly enlarged headgear and weapon profiles, clear mounted versus foot posture, visible artillery crews, and team-color cloth patches.

Generate seeded cosmetic variation without changing hitboxes: height within a narrow range, skin and hair palettes, cloth secondary color, pack or tool variants, stance offset, and dirt level.

Buildings assemble from modular foundations, wall bays, roofs, towers, doors, props, and era-specific upgrades. Damage variants expose beams, cracks, torn cloth, and fire points.

Generate collision and selection proxies separately from visual geometry.

Include an asset-preview route with turntable, neutral lighting, wireframe, normals, animation clips, LOD distances, bounds, texture memory, triangle counts, and palette variants.

Include a command-line bake or export step so procedural assets can be cached as optimized glTF if runtime construction becomes a loading bottleneck.

For content-complete quality, keep an optional Blender-to-glTF path documented for artists. Any external model must match the same naming, scale, skeleton, animation, material, LOD, and license validation rules. Do not block the playable build on unavailable proprietary tools.

Animation

Every mobile unit needs idle variants, walk or run, turn, attack wind-up and release, reload, hit reaction, ability, work actions where relevant, garrison or board transition, incapacitated, death, and decay or removal. Buildings need construction stages, production activity, upgrade, damage, fire, collapse, and ambient loops. Ships need idle bob, acceleration lean, turn lean, recoil, sail or engine response, damage, sinking, and wake states.

Animation state follows simulation state and authoritative event markers.

Blend clips with short role-specific transitions. Do not restart walk cycles on every snapshot.

Foot phase and movement speed should correspond closely enough to avoid obvious sliding.

Attack release frames must match projectiles and sound transients.

Nearby units may use full skeletal animation; distant units use reduced update frequency, GPU-driven animation, or baked vertex animation as supported.

Death poses use deterministic variants. Corpses fade into low-cost remains according to settings and performance budgets.

Add animation event inspection to the asset-preview tool.

Visual effects and feedback

Use pooled particles and decals for muzzle flash, smoke, dust, impact sparks, splinters, footprints, bloodless hit confirmation, water spray, wake, fire, healing, construction, capture, era advancement, dispatch arrival, and destruction.

Effects scale with camera distance and quality. Tactical readability always wins over density.

Team colors never tint smoke or fire in a way that confuses ownership.

Selected ranges, aura radii, firing arcs, minimum range, formation footprint, garrison radius, and placement influence appear only on request or relevant hover.

Invalid commands produce a brief red or amber ground response plus a concise reason. Do not rely on sound alone.

Screen shake, flashes, chromatic effects, motion blur, and camera impulses are restrained, adjustable, and disabled by reduced-motion settings.

Audio and music

Use Web Audio for mixing and Three.js positional audio or direct PannerNodes for world sources. The game must start only after a user gesture enables audio. Provide master, music, ambience, interface, voices, combat, and voice-chat buses with mute and dynamic-range presets.

Audio rules:

All audio must be original or licensed for redistribution and listed in THIRD_PARTY_ASSETS.md.

Until commissioned assets exist, synthesize functional original placeholders with Web Audio and mark them clearly in the asset manifest. Do not download or imitate AoE sounds or music.

Each important action has a family of variations to prevent repetition: selection, acknowledge, cannot comply, attack, retreat, construction, completion, research, dispatch, alert, capture, era up, cannon, musket, melee, impact, collapse, ship, water, wildlife, and UI.

Group selection plays one leader bark, not every unit. Rate-limit repeated combat and alert sounds by category and spatial cell.

Positional rolloff follows camera scale, with distant battles reduced into a low-frequency ambience layer rather than hundreds of active nodes.

Occlusion and indoor filtering may be approximated but must not make gameplay cues unreliable.

Provide subtitles or textual event equivalents for gameplay-relevant voice and alerts.

Create an adaptive original score system with exploration, development, threat, battle, crisis, victory, and defeat states. Use horizontally mixed stems and musically valid transition bars. The simulation emits intensity and state events; the music director smooths them and enforces minimum dwell times. Do not change music on every small skirmish. Placeholder stems may be procedurally synthesized, but production readiness requires reviewed original or licensed recordings.

Web workers and performance isolation

Run simulation, pathfinding, map generation, replay compression, and selected asset decoding away from the main UI thread. Use transferable typed arrays. Use SharedArrayBuffer only when the site is served over HTTPS with cross-origin isolation headers and all asset origins satisfy the policy. Provide a transferable-buffer fallback.

Do not put authoritative gameplay computation in GPU compute shaders. GPU computation may accelerate presentation-only particles, foliage, skinning, or culling because GPU arithmetic can vary across devices.

Build immutable versioned client and content bundles.

Security and anti cheat

Validate every command on the server for authenticated player, room membership, entity ownership, legal visibility where required, resources, cooldown, target, bounds, rate, sequence, and current match phase.

Use schema validation and maximum sizes on HTTP, WebSocket, scenario, deck, chat, and upload inputs.

Apply per-user, per-IP, per-room, and global rate limits with conservative exemptions for legitimate command bursts.

Protect against replayed join tokens, duplicate commands, sequence jumps, pathfinding bombs, entity-count abuse, malformed compressed data, zip bombs, prototype pollution, SQL injection, XSS, CSRF, SSRF, and secret exposure.

Use secure headers, TLS, origin validation, signed short-lived tokens, HttpOnly secure cookies, CSRF protection where applicable, prepared database access, and least-privilege service credentials.

Do not trust client clocks or local storage for penalties, rank, unlocks, results, or purchases.

Record authoritative command anomalies and checksum failures. Build review tooling before punitive automation.

Add dependency scanning, secret scanning, lockfile integrity, code review checks, and a vulnerability response process.

Voice and chat reporting must preserve only the evidence permitted by the stated privacy policy. Do not record voice by default.

Automated tests cover core rules and at least one failure path.

Performance impact is measured in a representative scenario.

Errors are visible and recoverable.

Content IDs and protocol versions are stable or migrated.

PROJECT_STATE.md and the relevant generated reference are current.
